# Search Core

`SearchCore.execute(SearchPlan)` is backend-only retrieval infrastructure. It does
not generate answers, interpret `purpose`, call AI, or read document binaries.

## Boundaries

- `repository.ts`: authenticated user → owned Subject scope → owned Neuron scope
  → candidate text/metadata. PostgreSQL narrows candidates before content loads.
- `ranking.ts`: shared context chunking, query templates, token/phrase scoring and
  deduplication. `knowledge/retrieval.ts` is a compatibility DTO adapter over it.
- `core.ts`: plan validation, multiple requests, canonical source identities,
  allowlisted output, and the navigation ranking profile for the existing palette.
- `KnowledgeService`: loads owned sources; does not search across the hierarchy.
- `local-answer.ts`: legacy local V0 answer compatibility only, outside Search Core.

`SearchRepository` can be replaced without changing plan consumers. A future
planner must attach the authenticated user ID on the server, never trust a user
ID generated by a model or supplied in an HTTP request.

## Results

`RetrievedInformation.plan` records resolved Subject/Neuron IDs. Each request
retains its query, request ID, found flag, and ranked items. `found` means matching
information exists, not that the question can be answered. Missing information
returns `found: false, results: []`. The canonical `sources` list contains metadata
and provenance once per parent source; overlapping requests may reference the
same stable SHA-256 chunk identity.

Global Search constructs one plan with the `navigation` profile. That profile
preserves exact/prefix/substring title priority and recency for navigation. Context
ranking uses soft token overlap, rarity, headings and phrase bonuses. Both profiles
share scope resolution, repository, source DTOs, result assembly, limits and ownership.

## V1 limits and omissions

- Up to 10 requests; query length up to 4,000 characters; unique request IDs.
- Default 50 spaces / 200 neurons; hard caps 100 / 500.
- Default 20 results/request; hard cap 50. Candidate window per source type is
  twice the requested result limit, capped at 50, ordered by update time then ID.
- Scope resolution uses deterministic ID order and literal name matching.
- Candidate windows are bounded: this is not exhaustive retrieval or semantic search.
- Related-neuron traversal is reserved and explicitly rejected when requested.
- Documents expose filename, MIME, size and timestamp only. Existing stored-name,
  extension and checksum navigation matches remain internal repository capabilities.
- No schema changes, external search service, embeddings, or LLM calls.
